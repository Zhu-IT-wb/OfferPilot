# 编码任务 5.1：项目训练编码实施计划

> 本文供后续编码 Agent 接续使用。每完成一个阶段，必须更新“当前进度”、阶段检查项和进度日志。

## 1. 当前结论

八股训练 MVP 已基本完成，可以开始项目训练。

现有可复用能力：

- Markdown 题库、单题卡片、章节导航和每日推荐；
- 文字回答、语音录制与百炼 ASR；
- AI 结构化评价、事实错误校验和服务端计分；
- Attempt、Progress、Assignment 原子完成和并发租约；
- 飞书网页登录态、用户隔离和机器人提醒。

不阻塞项目训练的八股遗留项：

- 飞书 Android、iOS 真实设备语音验收；
- 固定真实模型评分集及模型切换回归；
- 审查中剩余的非 P0 优化。

项目训练 MVP 定义：选择一个自己的项目，由 AI 面试官连续追问，每题回答后立即反馈，最后生成训练总结。

必须形成以下闭环：

```text
创建项目档案
  → 开始训练并看到第一题
  → 文字或语音回答
  → 获得可信评价
  → 根据回答动态追问
  → 完成训练并查看总结
  → 恢复历史或重练薄弱主题
```

## 2. 本阶段范围

### 2.1 必须实现

- Project Profile 创建、更新、归档和历史版本；
- 项目证据片段；
- Project Training Session、Turn、Answer；
- 项目介绍题和动态追问；
- 项目专用评价维度；
- 文字和语音回答；
- 中断恢复、幂等和原子完成；
- 训练总结、历史和薄弱主题重练。

### 2.2 明确不实现

- 混合八股的完整模拟面试；
- 真正的视频会议、WebRTC 和数字人；
- 实时语音、实时字幕和打断；
- Git 仓库或源代码自动解析；
- 外部网站抓取；
- 项目回答的唯一“正确答案”；
- 机器人聊天消息中完成整场训练。

这些内容属于编码任务 5.2 或后续版本。

## 3. 开发原则

### 3.1 采用纵向切片

不要先批量建设所有表、类和页面。每个阶段都要形成可运行的 HTTP 闭环：

```text
项目档案可保存
  → Session 可创建和恢复
  → 一道题可回答和评价
  → 多轮动态追问
  → 语音接入
  → 总结和历史
```

### 3.2 一个主要测试 seam

主要验收 seam 是网页 HTTP 行为：

```text
创建 Project Profile
  → 创建 Session
  → 获取当前 Turn
  → 提交 Answer
  → 获得评价和下一 Turn
  → 完成并获取 Summary
```

只为模型异常、检索排序、证据校验和事务冲突补充模块级测试。不要测试私有方法或完整 Prompt 文本。

### 3.3 一个深模块

`ProjectTrainingWorkflow` 是主要模块，外部 interface 控制在四个行为：

```text
start(owner_id, project_id, options) -> TrainingOutcome
submit_answer(owner_id, session_id, turn_id, answer) -> TrainingOutcome
resume(owner_id, session_id) -> TrainingOutcome
finish(owner_id, session_id) -> TrainingSummary
```

问题规划、证据选择、追问、评价、事务和恢复隐藏在模块内部。网页和未来机器人入口不能各自实现追问逻辑。

### 3.4 本地记录是权威记录

Project Profile、Session、Turn、Answer、Topic Progress 和 Summary 都是 OfferPilot Record。飞书卡片、消息和文档只作为入口或视图。

### 3.5 MVP 不引入独立向量数据库

第一版仍使用 RAG，但先采用结构化字段和证据片段检索：

- Project Profile 字段直接进入上下文组装；
- 补充 Markdown 按标题和段落切分为 Evidence；
- 按当前主题、技术栈和关键词召回；
- 保存 Evidence ID、来源和 content hash；
- 材料规模变大后在模块内部增加 embedding rerank，不改变外部 interface。

## 4. 领域模型

### 4.1 ProjectProfile

```text
id, owner_id, name, target_role
background, responsibilities[], tech_stack[], architecture
key_decisions[], technical_challenges[], metrics[], outcomes[]
resume_description, supplemental_text
status: active | archived
version, content_hash, created_at, updated_at
```

约束：

- 所有访问带 owner ID；
- Session 引用明确的 Profile version；
- 历史版本不能因编辑当前档案而失去解释能力；
- metrics 保存名称、数值、单位和测量方式；
- 档案可不完整，但页面必须显示缺失项。

### 4.2 ProjectEvidence

```text
id, project_id, project_version
source_field, heading, content, topic_tags[]
content_hash, order
```

用途：为非假设问题提供来源、检查回答一致性，并防止模型补造项目事实。

### 4.3 ProjectTrainingSession

```text
id, owner_id, project_id, project_version
target_role, goal, difficulty
max_turns, status, current_turn_id
started_at, completed_at, created_at
```

状态：`ready | in_progress | completed | abandoned`。

MVP 默认一次只训练一个项目，默认 6 题，最少 3 题，最多 10 题。

### 4.4 ProjectTrainingTurn

```text
id, owner_id, session_id, parent_turn_id, sequence
theme, question_kind, question_text
generation_reason, source_evidence_ids[], hypothetical
status, answer_id, created_at, completed_at
```

`question_kind`：`opening | evidence | design | tradeoff | reliability | metrics | hypothetical`。

约束：

- 第一题固定为项目介绍题；
- 非假设题必须关联 Evidence 或父 Turn Answer；
- 假设题明确使用“假设”或“如果”；
- 同一主题最多连续追问两次；
- 已完成 Turn 不能被模型修改。

### 4.5 ProjectTrainingAnswer

```text
id, owner_id, session_id, turn_id, submission_id
answer_text, answer_source, submitted_at
evaluation_status, evaluation_payload, overall_score
```

约束沿用八股答案：同 owner + submission ID 唯一，同一 Turn 只有一个活跃评价，音频不入库，失败 Answer 可用原 submission ID 重试。

### 4.6 ProjectTopicProgress

主题：`project_overview | ownership | architecture | technical_depth | tradeoff | metrics | reliability | troubleshooting | communication`。

```text
owner_id, project_id, topic
attempt_count, mastery_score, last_score
last_practiced_at, last_detected_gaps[]
```

MVP 只用于总结和下一场训练选题，不接每日机器人推送。

## 5. AI 面试官设计

### 5.1 默认主题计划

1. 项目概述；
2. 个人职责；
3. 架构或核心设计；
4. 技术难点；
5. 方案取舍；
6. 性能、故障或结果。

高级难度增加容量扩大十倍、关键依赖故障、数据一致性、降级恢复和替代架构。

### 5.2 动态追问信号

```text
vague_claim          回答过于宽泛
missing_ownership    没说清个人贡献
missing_metric       提到效果但没有数据
technology_choice    出现技术选型
reliability_claim    出现高可用、稳定性或故障主张
scalability_claim    出现高并发、性能或扩容主张
unsupported_claim    项目档案缺少对应证据
contradiction        与档案或前文矛盾
topic_complete       当前主题已经充分
```

模型只返回信号和候选追问，服务端规则决定是否追问，避免无限循环。

### 5.3 每轮模型上下文

只提供：

- 当前 Project Profile 摘要；
- 当前主题相关 Evidence；
- 最近两轮问题和回答；
- 已覆盖主题；
- 目标岗位和难度；
- 禁止补造事实规则。

不提供全部历史 Session、无关项目或完整补充材料。

### 5.4 结构化评价

模型输出包含：

```text
dimension_scores
strengths[]
missing_details[]
unsupported_claims[]
contradictions[]
answer_evidence[]
follow_up_signals[]
feedback
improved_outline[]
suggested_follow_up
```

评分维度及建议权重：

- 个人贡献 20%；
- 技术深度 20%；
- 数据证据 15%；
- 方案取舍 15%；
- 故障与边界意识 10%；
- 表达结构 10%；
- 表达清晰度 10%。

服务端负责维度白名单、分数边界、回答 quote 校验、Evidence ID 校验和最终计分。模型结构非法时重试一次；模型不可用时保存失败答案，不生成假评分。


语音复用现有 `SpeechTranscriptionService`，新增 Turn 绑定接口：

```text

```

```text

```

训练页顶部显示项目、主题、题号和剩余题数；中间只显示当前问题；底部语音为主、文字为辅；评价后显示做得好的点、缺少内容、可疑表述和改进结构。

所有接口使用飞书网页登录态；owner ID 不能由客户端提交。其他用户资源统一表现为 not found。

## 7. 原子性与恢复

复用八股 P0 修复形成的事务模式：

1. 创建 Answer 并抢占 Turn 活跃租约；
2. 在短事务之外调用模型；
3. 模型返回后计算 Topic Progress 和候选下一 Turn；
4. 在一个短事务中原子完成 Answer、Turn、Session、Progress 和下一 Turn；
5. CAS 冲突时重新读取进度并有限重试；
6. 模型失败或任务取消时释放租约；
7. 进程崩溃后允许原 submission ID 恢复。

必须防止：

- Answer completed，但 Turn 仍 pending；
- Turn completed，但 Session.current_turn_id 未更新；
- 两个并发回答创建两个下一 Turn；
- 模型失败后丢失用户回答；
- 刷新页面后重新生成第一题。

## 9. 测试矩阵

### 9.1 Project Profile

- 创建、更新、归档、列表；
- 必填字段与长度限制；
- owner 隔离；
- version、content hash 和 Evidence 稳定 ID；
- 历史 Session 引用旧版本；
- SQLite 重启恢复。

### 9.2 Session 与 Turn

- 第一题确定性；
- 刷新恢复；
- completed/abandoned 不可继续回答；
- parent Turn 与 sequence；
- 同一轮只创建一个下一 Turn。

### 9.3 评价

- 维度白名单和分数边界；
- 非法 JSON、缺字段和未知信号；
- answer quote 不存在时拒绝证据；
- Evidence ID 不存在时拒绝矛盾判断；
- AI 不可用时不生成假评分；
- 档案证据不足时输出 unsupported claim，而不是事实错误。

### 9.4 并发与故障

- 相同 submission ID 返回相同 Answer；
- 不同 submission ID 并发只产生一个活跃评价；
- 取消释放租约；
- 过期租约使用原 ID 恢复；
- Progress CAS 冲突重算；
- 事务失败完整回滚；
- 并发请求不能创建两个下一 Turn。

### 9.5 页面与语音

- 表单错误提示；
- 开始、恢复、完成和放弃；
- 录音开始、停止、自动停止和重录；
- ASR 重试与文字降级；
- 反馈 HTML 转义；
- 切题释放音轨；
- 手机窄屏可用；
- 完成后不能重复提交旧 Turn。

## 10. 固定验收样例

至少准备两个不含敏感信息的项目。

### 样例 A：高并发订单系统

覆盖 Redis、MySQL、消息队列、幂等、限流、降级、性能指标和故障恢复。

### 样例 B：AI Agent 求职助手

覆盖 LLM 调度、Tool Calling、状态管理、结构化输出、Provider 失败、数据一致性、成本和延迟。

每个项目准备六类回答：

1. 完整且包含数据；
2. 只说团队，没有个人贡献；
3. 技术名词很多但没有方案取舍；
4. 缺少指标；
5. 前后矛盾或档案不支持的夸大主张；
6. 明确表示不知道。

真实模型验收需要保存模型 ID、Prompt 版本、输入、结构化输出、人工预期和实际差异，但不加入默认自动化测试，避免持续计费。

## 11. 风险与控制

### 风险 1：模型补造项目事实

控制：Evidence ID、假设题标记、最小上下文、unsupported claim、固定验收集。

### 风险 2：把项目表达分误当项目真实性

控制：页面明确评价范围；不输出绝对真假判断；只指出证据不足、内部矛盾和技术解释问题。

### 风险 3：追问无限循环

控制：主题计划、同主题追问上限、最大 Turn 数和服务端追问决策。

### 风险 4：项目资料泄露

控制：owner 隔离、只检索必要片段、日志脱敏、音频不持久化、限制外部模型上下文。

### 风险 5：复制八股模块形成两套录音和事务逻辑

控制：复用 `SpeechTranscriptionService` 和已经验证的租约/原子完成模式，只新增项目领域的规划与评价。

### 风险 6：过早引入向量数据库拖慢闭环

控制：MVP 使用结构化字段和 Evidence 片段；embedding rerank 延后且隐藏在模块内部。

### 风险 7：一个 HTML 文件继续膨胀

控制：项目训练页面从第一版就拆分静态资源和录音状态模块，不复制八股页面中的压缩单行脚本。

每次开始编码前：

1. 阅读 `编码任务5-面试训练与模拟面试需求说明.md` 和本计划；
2. 查看“当前进度”和最近一条进度日志；
3. 运行 `git status --short`，保护用户已有修改；
4. 验证上一阶段的完成证据；
5. 只把一个纵向切片设为 `in_progress`；
6. 完成后更新检查项、阶段表和进度日志；
7. 不因为自动化测试通过就跳过真实页面和手机验收；
8. 不把混合模拟面试偷偷加入项目训练 MVP；
9. 不把项目评分当成项目真实性证明；
10. 不在没有固定验收样例前随意调整计分权重；
11. 外部模型调用前确认不会泄漏完整敏感项目材料；
12. 完成一个阶段后再进入下一阶段，不留下无法运行的横向半成品。
