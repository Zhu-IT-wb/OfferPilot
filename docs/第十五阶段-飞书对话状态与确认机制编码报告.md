# 第十五阶段：飞书对话状态与确认机制编码报告

## 1. 阶段目标

本阶段目标是解决 OfferPilot 接入飞书后的第一个真实可用性问题：用户在飞书里往往不是一次性说完整指令，而是多轮补充信息。

需要支持的核心流程：

```text
用户：我今晚有个面试，深信服二面
OfferPilot：缺少岗位，请补充
用户：岗位是 AI 应用开发
OfferPilot：我将新增深信服 AI 应用开发二面，执行前需要你确认
用户：确认
OfferPilot：已创建投递记录
```

## 2. 本阶段完成内容

### 2.1 新增会话状态管理

新增文件：

```text
backend/app/agents/conversation.py
```

提供：

- `PendingAgentAction`
- `InMemoryConversationStore`
- `get_default_conversation_store`

当前使用进程内存保存用户最近一条待补全或待确认动作，按 `source:user_id` 隔离不同来源和不同用户。

说明：

- 这是 MVP 实现；
- 服务重启后 pending 状态会丢失；
- 后续可以迁移到 SQLite 或 Redis。

### 2.2 扩展 AgentOrchestrator

修改文件：

```text
backend/app/agents/orchestrator.py
```

新增能力：

- 支持 `user_id` 和 `source`；
- 支持 `确认` / `取消`；
- 支持补槽消息，例如：
  - `岗位是 AI 应用开发`
  - `公司是深信服`
  - `时间是今晚`
  - `二面`
- 写入动作仍然需要确认；
- `confirmed=true` 的 API 旧语义保持不变，仍表示确认当前请求。

### 2.3 飞书回调接入用户级上下文

修改文件：

```text
backend/app/api/routes/feishu.py
```

飞书回调现在会将用户 `open_id` 传给 Agent：

```text
source=feishu
user_id=<feishu open_id>
```

这样不同飞书用户的待确认动作不会互相串。

### 2.4 飞书事件去重

飞书真实回调可能因为重试或网络抖动造成同一事件重复到达。

本阶段新增内存去重：

- 优先使用 `header.event_id`；
- 其次使用 `event.message.message_id`；
- 已处理过的事件不会再次调用 Agent；
- 避免同一条用户消息触发重复回复。

### 2.5 规则兜底增强

修改文件：

```text
backend/app/agents/intent_classifier.py
```

增强了无 LLM 或 LLM 解析失败时的规则识别：

```text
我今晚有个 AI 应用开发面试，深信服二面
```

可识别为：

```json
{
  "intent": "add_application",
  "slots": {
    "company": "深信服",
    "role": "AI 应用开发",
    "interview_time": "今晚",
    "round": "二面"
  }
}
```

同时调整了优先级，避免将 `复盘今天的面试` 误判为新增投递。

新增或更新测试：

```text
backend/tests/test_agent_orchestrator.py
backend/tests/test_agent_message_route.py
backend/tests/test_feishu_events.py
```

## 5. 当前限制

- 会话状态仍是进程内存，服务重启后会丢失；
- 目前补槽能力重点覆盖新增投递记录；
- 还没有把“确认中断/过期时间”持久化；
- 还没有在飞书多维表格中展示投递记录；
- 复杂自然语言仍主要依赖 DeepSeek。
