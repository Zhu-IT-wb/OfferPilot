## Windows 录制流程

推荐使用 [ScreenToGif 官方发布页](https://github.com/NickeManarin/ScreenToGif/releases/latest)提供的 Windows 工具，自行下载并打开。本次文档整理不安装录制软件。

1. 先预演一次完整流程，准备演示账号、公开仓库和真实可查询的知识库资料。录制区域内隐藏个人信息、密钥与无关通知。
2. 打开录制器，拖动和调整录制区域。建议输出宽度为 960–1200 像素；先放大应用界面再局部录制，避免把 4K 全屏缩小到文字不可读。
3. 将帧率设为约 12 fps，这是兼顾体积与交互流畅度的建议值。框住当前操作和结果所需区域后开始录制。
4. 完成脚本，关键确认卡片、引用、代码行号或最终结果各停留约 2 秒，再停止录制并进入编辑器。
5. 在编辑器裁掉开头、结尾和无关等待。长任务可以剪掉等待或加速，若改变时间表现，在画面或图片说明中注明“等待已裁剪”或“等待已加速”。
6. 导出为 GIF，存入根目录 `show/` 并同步 README 的相对路径。保留已有素材文件名；下方脚本中的英文文件名仅供新增素材参考。先使用内置编码器即可；可选 Gifski 编码器需要额外依赖。
7. 打开导出的 GIF，检查文字、节奏、结果和循环衔接。建议每段约 15–30 秒，复杂流程尽量不超过 45 秒，体积以约 5–10 MB 为压缩目标；这不是 GitHub 的文件限制。

保留编辑工程或 MP4 素材，便于以后重新剪辑。官方操作参考：[录制器](https://github.com/NickeManarin/ScreenToGif/wiki/Help-%E2%96%AA-Recording-%F0%9F%93%B9)、[GIF 导出](https://github.com/NickeManarin/ScreenToGif/wiki/Help-%E2%96%AA-Editor-%E2%9C%8F%EF%B8%8F-%E2%96%AA-Exporting-your-project-%F0%9F%92%BE-%E2%96%AA-Gif)。

## 后续补录脚本

以下是原先规划的五段完整流程，供补录或替换素材参考，不代表当前已录制内容。表中的顺序与建议文件名不对应上方六份现有素材。

| 顺序 | 主题 | 目标文件 | 建议时长 |
| --- | --- | --- | --- |
| 01 | 投递补充与确认 | `01-application-confirmation.gif` | 20–30 秒 |
| 02 | 面试记录与飞书日历 | `02-interview-calendar.gif` | 20–30 秒 |
| 03 | 知识库问答与引用 | `03-knowledge-rag.gif` | 15–30 秒 |

### 01 投递补充与确认

**前置：** 飞书机器人与多维表格可用；准备好演示用表格视图，并确认这条演示记录尚未存在。

**用户原话：**

> 我今天投递了演示公司的Agent开发岗位。

收到确认卡片后，继续发送：

> 确认，补充一下base深圳。

**录制顺序：** 首条消息 → 第一张确认卡片 → 补充消息 → 含深圳的新确认卡片 → 回复“确认” → 切到表格查看。

**应录到的真实结果：** 补充后先出现新卡片，核对公司、岗位和 base 深圳；在新卡片再次确认后才写入表格。表格中的实际记录与确认内容一致，不把补充消息本身剪成已经完成写入。

### 02 面试记录与飞书日历

**前置：** 已有“演示公司 / Agent开发”投递记录；日历集成已配置，并在正式录制前预演到真实日程创建成功。当前已有日历邀请素材；重新录制时仍需核对实际创建结果。

**用户原话：**

> 演示公司约我后天下午3点一面，请帮我记录并同步飞书日历。

**录制顺序：** 发送消息 → 按实际追问补齐信息 → 核对具体日期、15:00 和一面 → 完成流程要求的确认 → 查看面试记录与飞书日历中的日程。

**应录到的真实结果：** 面试安排已保存，飞书日历中能打开对应事件，日期、时间和公司一致。“后天”以录制当天为准；仅有助手声称同步成功、申请授权或待确认画面不足以作为成功素材。

### 03 知识库问答与引用

**前置：** 知识库中已导入联合索引与最左匹配相关资料，检索服务可用，且原始资料能被核对。

**用户原话：**

> MySQL联合索引为什么要遵循最左匹配原则？结合知识库说明，并给出引用来源。

**录制顺序：** 发送问题 → 展示真实返回的解释 → 滚动到引用来源 → 展开或查看实际可用的来源信息。

**应录到的真实结果：** 回答说明联合索引的排序与最左匹配关系，并给出知识库实际返回的来源标识或片段；来源与回答内容对应。为关键解释和引用各保留可阅读的停留时间。

### 04 GitHub 源码分析与确认

**前置：** 打开 Web 项目训练页 `/study/projects`，选择已预演可分析的公开 GitHub 仓库。提前准备如实描述个人工作的文字。

**用户原话（填写到“个人职责”，录制前替换方括号）：**

> 我的个人职责是[实际负责的模块与工作]；其他部分由[原作者或团队]完成。

如仅学习或复现开源项目，应把自己的学习、复现或修改范围写清楚。

**录制顺序：** “分析 GitHub 项目” → 填写公开仓库地址 → “开始分析” → 展示生成草稿和代码证据 → 补充个人职责 → “确认并创建档案”。

**应录到的真实结果：** Web 导入流程实际完成；至少一项分析结论有可读的真实文件路径、行号和对应代码证据；个人职责经用户补充、确认后形成项目档案。分析等待可裁剪并注明，保留分析前后的真实状态。

### 05 项目训练与总结

**前置：** Web 中已有确认后的项目档案，项目来源、个人职责和目标岗位已核对。先预演问答，按实际问题准备两段真实回答。

**用户原话示例（根据当前题目和真实项目补全后输入）：**

> 我负责[模块]，用[方案]解决了[问题]；个人实现的范围是[职责边界]，对应证据是[文件与行号或验证结果]。

第二轮根据页面实际追问作答：

> 针对刚才的[追问点]，我选择[方案]是因为[约束]；比较过[备选方案]，并通过[真实验证方式]确认了[结果]。

**录制顺序：** 从项目档案进入训练 → 展示题目 → 提交第一轮回答 → 展示反馈和实际后续问题 → 提交第二轮回答 → 展示反馈 → “提前结束并生成总结” → 确认并查看总结。

**应录到的真实结果：** 两轮答案均实际提交，页面返回对应反馈与后续问题，结束后生成这次训练的总结。回答应回应当前题目，不能把预写的问答或历史报告拼接成本次结果。

通用 mock 面试当前仅首问，不纳入上述多轮训练演示；普通 Task 不作为核心演示。八股复习与每日刷题目前已有页面截图，可按需补充实际作答和反馈过程。
