# OfferPilot 需求分析与技术方案

版本：v0.1  
日期：2026-06-17  
定位：面向计算机秋招准备的个人求职 Agent  
当前阶段：需求澄清与技术预研  

## 1. 项目背景

OfferPilot 的出发点不是做一个泛泛的学习助手，也不是做一个只会聊天的 AI Bot，而是解决计算机学生在实习、秋招准备过程中长期存在的执行问题。

目标用户每天都知道自己应该刷题、背八股、投递岗位、准备面试、复盘面经，但这些事情通常分散在不同平台和文档中，缺少持续追踪。面试失败后，很多高价值信息没有被沉淀，导致每一场面试都像从零开始，项目被深挖答不上来的问题也会反复出现。

OfferPilot 要做的是把这些零散动作串成一个持续迭代的闭环：

```text
计划生成 -> 用户执行 -> 打卡/提交 -> AI 评价 -> 数据沉淀 -> 下一轮计划
```

第一版只服务个人用户，尤其是准备计算机类实习、秋招的人。后续如果系统稳定，再考虑扩展成多用户产品。

## 2. 一句话定义

OfferPilot 是一个基于飞书工作台的秋招执行 Agent，通过飞书机器人、多维表格和自研后端 Agent 编排，将 LeetCode 刷题、八股复习、投递管理、面试复盘和模拟面试串成一个持续迭代的求职准备系统。

## 3. 用户画像

### 3.1 第一阶段目标用户

第一阶段只面向一个很具体的人群：

- 计算机相关专业学生；
- 正在准备实习、暑期实习、秋招或春招；
- 目标岗位包括 Java 后端、Python 后端、AI 应用开发、Agent 开发、算法工程偏应用方向；
- 需要刷 LeetCode；
- 需要背 Java、数据库、Redis、计算机网络、操作系统、Spring 等八股；
- 需要管理投递记录；
- 需要在面试后复盘；
- 容易拖延，缺少稳定执行系统。

### 3.2 当前最小用户

当前最小用户就是项目作者本人。

这非常重要，因为第一版不需要考虑复杂的团队权限、商业化、多租户、支付、运营后台等问题。只需要围绕一个真实用户，把闭环做通。

## 4. 核心痛点

### 4.1 准备事项多，但没有统一入口

秋招准备至少包括：

- LeetCode 刷题；
- 八股复习；
- 项目深挖；
- 简历优化；
- 岗位投递；
- 笔试安排；
- 面试安排；
- 面试复盘；
- 薄弱点补强。

这些内容通常分散在浏览器收藏夹、Excel、飞书文档、聊天记录、Notion、脑子里，导致执行时很容易丢失上下文。

### 4.2 知道该做，但缺少每日推力

用户并不是不知道要刷题和背八股，而是每天缺少明确的“今天做什么”。如果只是写一句“今天刷题”，执行难度仍然很高。

系统应该具体到：

- 今天刷哪一道题；
- 为什么刷这道题；
- 这道题属于哪个高频考点；
- 做完之后要如何打卡；
- 没做完会如何延期或重新安排。

### 4.3 面试复盘没有沉淀

很多面试结束后，用户只记得“挂了”“答得不好”，但没有把问题转化为可执行任务。

例如一次面试中 Redis 缓存击穿没答好，理想流程应该是：

```text
面试记录 -> AI 提取薄弱点 -> 生成 Redis 复习任务 -> 安排未来几天追问 -> 再次模拟面试验证
```

### 4.4 项目深挖能力不足

很多简历项目在文档上看起来很强，但面试官一深挖就答不上来。

系统应该帮助用户把项目拆成可训练的问题树：

- 为什么这么设计？
- 有没有替代方案？
- 遇到过什么问题？
- 如何优化？
- 如何保证安全性？
- 如何处理异常？
- 如果流量变大怎么办？
- 如果面试官继续追问，下一层怎么答？

### 4.5 AI 使用零散，没有形成流程

用户可能会临时问 AI：

- 帮我改简历；
- 帮我模拟面试；
- 帮我总结面经；
- 帮我制定计划。

但这些请求彼此独立，没有数据沉淀。OfferPilot 要把 AI 从“临时聊天工具”变成“持续了解用户状态的执行 Agent”。

## 5. 产品目标

### 5.1 第一阶段目标

第一阶段目标是做一个个人可用的秋招执行系统，重点是把主流程跑起来。

必须做到：

- 用户可以通过飞书机器人与系统交互；
- 系统可以生成每日任务；
- 系统可以记录 LeetCode、八股、项目深挖、投递、面试复盘；
- 系统可以根据用户历史表现安排下一步任务；
- 用户可以在飞书多维表格中查看结构化数据；
- 系统能基于 DeepSeek 对用户回答和复盘进行分析。

### 5.2 非目标

第一阶段不做：

- 多用户 SaaS；
- 完整 Web 前端；
- 实时语音模拟面试；
- 自动登录 LeetCode 并抓取所有提交；
- 复杂推荐算法；
- 付费体系；
- 企业级权限管理；
- 移动端 App。

这些都可以后续做，但不应该进入 MVP。

## 6. 系统整体形态

### 6.1 用户如何使用

用户主要通过飞书使用 OfferPilot。

典型使用方式：

- 早上收到飞书机器人推送的今日任务；
- 在飞书中回复“完成”“跳过”“延期”；
- 在飞书中提交刷题思路、八股回答、面试复盘；
- 在飞书中发起模拟面试；
- 在飞书多维表格中查看投递记录、任务记录和薄弱点。

用户不需要打开一个新的网站，也不需要安装新的 App。

### 6.2 为什么选择飞书

飞书适合作为入口和工作台，原因是：

- 飞书机器人可以做自然语言交互；
- 飞书消息可以做每日提醒；
- 飞书多维表格适合存储投递记录、任务、题库、面试记录；
- 飞书文档适合存储简历、项目文档、面经；
- 当前实习环境与飞书生态相关，项目可以和实习经历形成呼应。

但飞书不适合作为全部逻辑的承载平台。复杂 Agent 编排、模型调用、任务状态机、评分逻辑、RAG 检索等能力应该放在自研后端中。

### 6.3 核心架构

```text
用户
  |
  | 飞书消息 / 飞书表格
  v
飞书机器人 / 飞书多维表格
  |
  | 事件回调 / API 调用
  v
OfferPilot 后端服务
  |
  | 意图识别 / Agent 编排 / Tool Calling
  v
DeepSeek / 其他大模型
  |
  v
工具层：任务工具、题库工具、投递工具、复盘工具、评分工具
  |
  v
飞书多维表格 / 本地数据库 / 向量库
```

### 6.4 关键原则

- 飞书负责交互和数据展示；
- 后端负责 Agent 编排和业务逻辑；
- 大模型负责理解、生成、评分、总结；
- 多维表格负责第一阶段的数据可视化和手动修正；
- 本地数据库负责系统内部状态；
- 第一版以可用为先，不追求过度自动化。

## 7. 功能模块

## 7.1 每日任务模块

### 7.1.1 模块目标

每日任务模块是系统的核心入口。它负责每天把用户拉回秋招准备主线。

它不只是提醒用户“该学习了”，而是要明确告诉用户：

- 今天刷哪道题；
- 今天背哪几个八股；
- 今天练哪个项目问题；
- 今天是否有面试；
- 昨天哪些任务没完成；
- 今天最优先补什么。

### 7.1.2 典型交互

早上 9 点，飞书机器人发送：

```text
早上好，今天的秋招任务如下：

1. LeetCode：206. 反转链表
   考点：链表、双指针、基础高频
   链接：https://leetcode.cn/problems/reverse-linked-list/

2. 八股：HashMap 扩容机制
   要求：口述 2-3 分钟，覆盖扩容触发条件、resize 过程、JDK 1.8 优化。

3. 项目深挖：云聚图库为什么使用 Caffeine + Redis 两级缓存？

4. 投递任务：新增 3 个目标岗位。

昨天未完成：Redis 缓存击穿复盘。
建议优先级：八股 > 项目深挖 > LeetCode > 投递。
```

用户回复：

```text
完成 LeetCode，思路是用 prev、cur、next 三个指针依次反转链表，时间 O(n)，空间 O(1)。
```

系统回复：

```text
通过。你覆盖了核心思路和复杂度。
建议补充：说明循环结束条件，以及为什么需要提前保存 next。
已记录完成。
```

### 7.1.3 任务类型

第一阶段任务类型包括：

- LeetCode；
- 八股；
- 项目深挖；
- 投递；
- 面试复盘；
- 简历优化；
- 自定义任务。

### 7.1.4 任务状态

任务状态建议如下：

- pending：待完成；
- in_progress：进行中；
- submitted：已提交，等待 AI 评价；
- passed：已通过；
- failed：未通过，需要重做；
- skipped：跳过；
- postponed：延期；
- expired：过期未完成。

### 7.1.5 任务生成策略

第一版不需要复杂算法，可以使用规则 + LLM 的方式。

规则部分：

- 每天最多 1 道 LeetCode；
- 每天 2-3 个八股问题；
- 每天 1 个项目深挖问题；
- 面试前一天增加模拟面试或 JD 分析任务；
- 面试后必须生成复盘任务；
- 未完成任务会延后，但最多连续延后 3 次，超过后降级或拆分。

LLM 部分：

- 根据薄弱点调整优先级；
- 根据投递岗位 JD 调整八股重点；
- 根据最近面试失败问题生成补强任务；
- 根据用户疲劳程度生成更可执行的计划。

## 7.2 LeetCode 刷题模块

### 7.2.1 模块目标

刷题模块的目标不是替用户做题，而是帮助用户建立稳定刷题节奏，并训练其讲题能力。

面试中很多时候不是只看是否 AC，而是看用户是否能解释：

- 为什么这么做；
- 时间复杂度是多少；
- 有没有边界条件；
- 有没有更优解；
- 和相似题的区别是什么。

### 7.2.2 题库来源

第一阶段可以手动维护高频题库，不需要自动爬取 LeetCode。

题库字段：

- 题号；
- 标题；
- 链接；
- 难度；
- 标签；
- 高频程度；
- 推荐阶段；
- 标准思路；
- 复杂度；
- 常见追问；
- 关联八股或算法模板。

### 7.2.3 是否需要自动打卡

完全自动化打卡不建议作为第一版核心能力。

原因：

- LeetCode 提交记录抓取可能不稳定；
- 自动判断 AC 不等于用户真正会讲；
- 平台登录、Cookie、接口变动会增加开发复杂度；
- 项目第一版应该优先跑通求职闭环。

第一版推荐半自动打卡：

1. 系统推送题目；
2. 用户刷题；
3. 用户提交文字版解题思路；
4. AI 判断思路是否覆盖核心点；
5. AI 追问边界条件或复杂度；
6. 通过后记录完成。

第二阶段再考虑自动校验：

- 用户提供 LeetCode 用户名；
- 系统根据题号检查公开提交记录；
- 或用户粘贴 AC 截图/代码；
- AI 结合代码进行分析。

### 7.2.4 AI 评价标准

LeetCode 答题评价不应该过度严格。只要用户能讲清楚核心思路，就可以通过。

建议评分维度：

- 核心算法是否正确；
- 是否提到关键数据结构；
- 是否说明时间复杂度；
- 是否说明空间复杂度；
- 是否考虑边界条件；
- 是否能用面试语言表达。

评分结果：

- passed：可以通过；
- weak_pass：大体正确，但需要补充；
- failed：核心思路错误，需要重做。

### 7.2.5 例子

题目：206. 反转链表

用户回答：

```text
用三个指针 prev、cur、next，每次保存 next，然后把 cur.next 指向 prev，再整体后移。
```

AI 评价：

```text
通过。核心思路正确。

建议补充：
1. 初始 prev = null，cur = head。
2. 循环条件是 cur != null。
3. 最终返回 prev。
4. 时间复杂度 O(n)，空间复杂度 O(1)。
```

## 7.3 八股复习模块

### 7.3.1 模块目标

八股模块用于训练用户的口述能力。目标不是让用户逐字背标准答案，而是让用户能够在面试中讲出核心点。

### 7.3.2 题库分类

第一阶段题库可以按照以下分类：

- Java 基础；
- Java 集合；
- JVM；
- 并发编程；
- Spring / Spring Boot；
- MySQL；
- Redis；
- 计算机网络；
- 操作系统；
- 分布式基础；
- 消息队列；
- AI 应用基础；
- RAG / Agent / Tool Calling。

### 7.3.3 题目结构

每道八股题建议包含：

- question：问题；
- category：分类；
- level：难度；
- keywords：核心关键词；
- standard_answer：标准回答；
- must_cover_points：必须覆盖点；
- nice_to_have_points：加分点；
- common_mistakes：常见错误；
- follow_up_questions：追问；
- review_interval：复习间隔。

例子：

```json
{
  "question": "HashMap 在 JDK 1.8 中的扩容机制是什么？",
  "category": "Java 集合",
  "level": "medium",
  "must_cover_points": [
    "默认负载因子 0.75",
    "容量达到阈值触发 resize",
    "容量通常扩为原来的 2 倍",
    "JDK 1.8 中链表长度超过阈值可能树化",
    "扩容后节点位置与原容量 bit 有关"
  ],
  "follow_up_questions": [
    "为什么容量通常是 2 的幂？",
    "HashMap 为什么线程不安全？",
    "ConcurrentHashMap 怎么解决并发问题？"
  ]
}
```

### 7.3.4 回答方式

第一版支持文本回答。

语音回答可以分阶段支持：

- v0.1：用户用手机输入法语音转文字，然后发送给飞书机器人；
- v0.2：用户上传音频文件，后端调用 ASR 服务转文字；
- v0.3：实时语音面试，支持边听边问。

DeepSeek 适合作为文本推理模型，不直接负责语音识别。语音识别需要接入额外 ASR，例如 Whisper、火山引擎、通义听悟或其他国产语音识别服务。

### 7.3.5 AI 评分标准

八股评分不追求严格，而是判断大意是否正确。

评分维度：

- 核心点覆盖率；
- 是否存在明显错误；
- 结构是否清晰；
- 是否能继续回答追问；
- 是否适合面试表达。

输出格式：

```text
评分：72/100
结论：弱通过

覆盖到的点：
- 说到了扩容阈值；
- 说到了容量翻倍；
- 说到了链表和红黑树。

缺失的点：
- 没讲清楚为什么容量是 2 的幂；
- 没讲清楚扩容后节点位置如何变化；
- 没提线程不安全。

建议你下次这样答：
...
```

### 7.3.6 复习机制

第一版可以使用简单的复习规则：

- passed：7 天后复习；
- weak_pass：3 天后复习；
- failed：明天复习；
- 面试中被问到但没答好：连续 3 天复习。

后续可以引入间隔重复算法，但第一版没必要复杂化。

## 7.4 投递记录模块

### 7.4.1 模块目标

投递模块用于管理公司、岗位、JD、状态和面试安排。

这个模块非常适合用飞书多维表格承载，因为用户可以直接查看和修改。

### 7.4.2 典型交互

用户在飞书中发送：

```text
新增投递：深信服，开发实习生，明天下午 3 点一面，JD 是 Java 后端，要求 Spring Boot、MySQL、Redis。
```

系统解析后写入多维表格：

```text
公司：深信服
岗位：开发实习生
方向：Java 后端
状态：一面待面
面试时间：2026-06-18 15:00
JD 关键词：Spring Boot, MySQL, Redis
下一步任务：今晚复习 Redis 缓存与云聚图库项目
```

系统回复：

```text
已记录深信服开发实习生面试。
根据 JD 和你的项目，今晚建议优先复习：
1. Caffeine + Redis 多级缓存；
2. MySQL 索引；
3. Spring Boot 常见问题；
4. 云聚图库权限设计。
```

### 7.4.3 投递状态

建议状态：

- planned：计划投递；
- submitted：已投递；
- written_test：笔试；
- interview_1：一面；
- interview_2：二面；
- interview_3：三面；
- hr：HR 面；
- offer：已 offer；
- rejected：已挂；
- no_response：无反馈；
- withdrawn：放弃。

### 7.4.4 多维表格字段设计

投递记录表字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 公司 | 文本 | 公司名 |
| 岗位 | 文本 | 岗位名 |
| 方向 | 单选 | Java 后端 / AI 应用 / Agent 开发 / Python 后端 |
| JD | 长文本 | 岗位描述 |
| JD 关键词 | 多选 | Spring Boot / Redis / RAG / Agent 等 |
| 投递时间 | 日期 | 投递日期 |
| 当前状态 | 单选 | 已投递 / 一面 / 二面 / 挂了 / offer 等 |
| 下一场时间 | 日期时间 | 笔试或面试时间 |
| 面试轮次 | 单选 | 一面 / 二面 / 三面 / HR |
| 复盘链接 | URL | 飞书文档或记录 |
| 薄弱点 | 多选 | Redis / JVM / 项目深挖等 |
| 下一步动作 | 文本 | AI 生成的下一步 |
| 优先级 | 单选 | 高 / 中 / 低 |

## 7.5 面试复盘模块

### 7.5.1 模块目标

面试复盘是系统最有价值的模块之一。它负责把每次面试的经验变成后续训练任务。

### 7.5.2 第一版输入方式

第一版建议支持文本复盘。

用户可以在飞书中发送：

```text
复盘深信服一面：
问了 HashMap、线程池、Redis 缓存击穿、云聚图库的权限设计。
我 Redis 答得不好，项目里 REST API Dispatcher 怎么做也讲得不清楚。
算法问了反转链表，写出来了，但是复杂度忘了说。
```

系统输出：

```text
已生成复盘。

本次面试暴露的问题：
1. Redis 缓存问题表达不完整；
2. Agent 调用业务接口的安全设计没有讲清楚；
3. 算法题讲解缺少复杂度分析；
4. 项目介绍没有主动突出权限复用。

已生成后续任务：
1. 明天复习 Redis 缓存击穿、穿透、雪崩；
2. 明天练习 REST API Dispatcher 项目深挖；
3. 后天刷 2 道链表题；
4. 后天进行一次 Java 后端模拟面试。
```

### 7.5.3 录音上传能力

用户希望上传面试录音，由 AI 自动分析。

这个能力可行，但建议放到第二阶段。

原因：

- 需要音频文件上传、存储和下载；
- 需要 ASR 服务；
- 面试录音可能包含隐私信息；
- 飞书消息中的音频文件处理需要额外调研；
- 长音频转写成本和时延更高。

第二阶段可以支持：

1. 用户上传录音；
2. 后端下载音频；
3. ASR 转文字；
4. LLM 分析转写稿；
5. 输出复盘；
6. 自动生成任务。

### 7.5.4 复盘输出结构

面试复盘建议输出固定结构：

- 面试基本信息；
- 被问到的知识点；
- 被问到的项目问题；
- 算法题；
- 回答较好的点；
- 回答较差的点；
- 面试官可能的评价；
- 下次改进建议；
- 转化后的任务；
- 需要加入题库的问题。

### 7.5.5 薄弱点沉淀

系统应该把复盘中的问题写入薄弱点表。

薄弱点字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 薄弱点 | 文本 | 例如 Redis 缓存击穿 |
| 分类 | 单选 | 八股 / 项目 / 算法 / 表达 |
| 来源 | 文本 | 深信服一面 |
| 严重程度 | 单选 | 高 / 中 / 低 |
| 出现次数 | 数字 | 反复被问的次数 |
| 最近出现时间 | 日期 | 最近一次出现 |
| 补强任务 | 关联 | 关联任务表 |
| 状态 | 单选 | 待补强 / 补强中 / 已缓解 |

## 7.6 模拟面试模块

### 7.6.1 模块目标

模拟面试用于解决“项目被深挖答不上来”的问题。

第一版不追求实时语音，而是先做文本模拟面试。文本版本已经足够支撑简历项目和实际训练。

### 7.6.2 模拟面试类型

支持以下模式：

- 八股快问快答；
- 项目深挖；
- JD 定制面试；
- 综合面试；
- 压力面试；
- 面试复盘后的补强面试。

### 7.6.3 典型交互

用户发送：

```text
开始模拟面试，岗位是 Java 开发实习，项目选云聚图库。
```

系统开始：

```text
好的，我们开始一面模拟。

请先用 2 分钟介绍一下云聚图库这个项目，你主要负责什么？
```

用户回答后，系统继续追问：

```text
你提到了 Caffeine + Redis 多级缓存。
为什么不只用 Redis？两级缓存会带来什么一致性问题？
```

用户回答后，系统继续追问：

```text
如果图片被更新了，本地 Caffeine 和 Redis 中的旧数据怎么处理？
```

结束后输出：

```text
本次模拟面试评分：68/100

主要问题：
1. 项目介绍结构不够清晰；
2. 缓存一致性回答不完整；
3. 对 Agent 调用业务接口的权限设计讲得不够主动。

建议：
...

已生成 3 个后续任务。
```

### 7.6.4 背后的用户数据

模拟面试需要读取用户数据：

- 简历；
- 项目文档；
- 投递岗位 JD；
- 历史面试复盘；
- 薄弱点；
- 最近任务完成情况。

这样模拟面试才不是泛泛地问八股，而是针对用户真实短板追问。

### 7.6.5 语音模拟面试

类似豆包的实时语音对话可以做，但不是第一阶段。

需要能力：

- ASR：语音识别；
- TTS：语音合成；
- 流式 LLM；
- 对话状态管理；
- 低延迟响应；
- 支持打断；
- 面试结束后的自动总结。

第一阶段先用文本模拟面试。第二阶段支持“上传语音回答”。第三阶段再考虑实时语音。

## 8. Agent 设计

## 8.1 Agent 总体职责

OfferPilot Agent 不应该只是调用一次大模型生成答案，而应该具备以下职责：

- 理解用户意图；
- 判断当前上下文；
- 调用合适工具；
- 写入结构化数据；
- 根据历史数据生成下一步；
- 对用户回答进行评价；
- 在必要时追问；
- 避免产生不可执行的计划。

## 8.2 意图分类

用户在飞书中可能发送自然语言，系统需要判断意图。

主要意图包括：

- get_today_tasks：查看今日任务；
- complete_task：完成任务；
- postpone_task：延期任务；
- add_application：新增投递；
- update_application：更新投递状态；
- add_interview_review：提交面试复盘；
- start_mock_interview：开始模拟面试；
- answer_question：回答八股/项目/算法问题；
- ask_help：普通咨询；
- summarize_week：周复盘。

## 8.3 Tool Calling 设计

后端应该把可执行动作封装成工具，不让大模型直接操作数据库或飞书 API。

工具示例：

- create_task；
- update_task_status；
- list_today_tasks；
- create_application；
- update_application_status；
- create_interview_review；
- extract_weaknesses；
- create_review_tasks；
- pick_leetcode_problem；
- pick_interview_question；
- grade_answer；
- send_feishu_message；
- write_bitable_record；
- query_user_profile。

### 8.3.1 工具调用原则

- 工具必须白名单注册；
- 工具参数必须有 schema；
- 后端校验参数，不信任模型；
- 危险操作需要二次确认；
- 工具执行结果必须回传给 Agent；
- 工具失败时要有可解释错误。

### 8.3.2 示例工具定义

```json
{
  "name": "create_task",
  "description": "Create a job-preparation task for the user.",
  "parameters": {
    "type": "object",
    "properties": {
      "title": { "type": "string" },
      "task_type": {
        "type": "string",
        "enum": ["leetcode", "interview_question", "project_deep_dive", "application", "review"]
      },
      "due_date": { "type": "string" },
      "priority": {
        "type": "string",
        "enum": ["high", "medium", "low"]
      },
      "source": { "type": "string" }
    },
    "required": ["title", "task_type", "due_date", "priority"]
  }
}
```

## 8.4 Agent 编排流程

### 8.4.1 用户消息处理流程

```text
飞书事件回调
  -> 验签
  -> 提取用户消息
  -> 读取用户上下文
  -> 意图识别
  -> 选择工具
  -> 执行工具
  -> 模型生成回复
  -> 写入日志
  -> 飞书回复用户
```

### 8.4.2 每日计划生成流程

```text

  -> 读取未完成任务
  -> 读取薄弱点
  -> 读取投递和面试安排

  -> 写入任务表
```

```text

  -> LLM 结构化提取
```

```text
  -> 生成后续任务
```

## 9. 数据设计

第一阶段可以同时使用飞书多维表格和本地数据库。

### 9.1 为什么不只用多维表格

多维表格适合展示和手动编辑，但不适合承载所有系统内部状态。

例如：

- Agent 对话日志；
- 工具调用日志；
- 模型请求结果；
- 幂等控制；
- 定时任务状态；
- 复杂查询；
- 向量检索。

这些更适合放在数据库中。

### 9.2 为什么不只用数据库

如果只用数据库，用户无法方便地查看和修改数据。飞书多维表格天然适合做个人工作台。

所以第一版建议：

- 飞书多维表格：用户可见的数据；
- 数据库：系统内部状态；
- 后端负责同步和读写。

### 9.3 推荐数据库

第一阶段推荐 SQLite 或 PostgreSQL。

如果只是本地开发和个人使用：

- SQLite 足够；
- 部署简单；
- 不用维护数据库服务。

如果准备部署到云服务器并长期使用：

- PostgreSQL 更合适；
- 后续可以加 pgvector；
- 更接近真实后端项目。

建议路径：

- v0.1 使用 SQLite；
- v0.2 切换 PostgreSQL；
- v0.3 增加向量库。

## 10. 飞书侧设计

## 10.1 飞书应用

需要创建一个飞书自建应用。

核心能力：

- 接收用户消息；
- 发送机器人消息；

参考官方能力：

- 发送消息 API：https://open.feishu.cn/document/server-docs/im-v1/message/create

### 10.2 飞书机器人命令

第一版命令不需要复杂，可以支持自然语言 + 少量固定命令。

固定命令示例：

## 11. 模型选择

### 11.1 第一阶段模型

第一阶段使用 DeepSeek 即可。

适合场景：

- 文本理解；
- 意图识别；
- 任务规划；
- 八股评分；
- 面试复盘；
- 模拟面试追问；
- 标准答案生成。

### 11.2 DeepSeek 的使用方式

推荐使用 OpenAI Compatible API 调用方式，便于以后替换模型。

后端中不要把 DeepSeek 写死在业务逻辑里，应该封装为 LLMClient：

```text
LLMClient
  -> DeepSeekProvider
  -> OpenAIProvider
  -> QwenProvider
```

这样后续可以切换到其他模型。

### 11.3 什么时候需要其他模型

需要额外模型的场景：

- 语音识别：Whisper / 火山 / 通义听悟；
- 语音合成：火山 TTS / Edge TTS / 其他服务；
- Embedding：DeepSeek 不一定提供合适 embedding，需要选择 Qwen Embedding、OpenAI Embedding 或本地 embedding；
- Rerank：后续做知识库检索时可接入 rerank 模型。

## 12. RAG 与知识库设计

### 12.1 第一阶段是否必须做 RAG

第一阶段不必须做完整 RAG。

因为用户数据量不大，简历、项目文档、题库都可以直接结构化读取。先用数据库和表格即可。

但从简历项目亮点角度，后续可以加入轻量 RAG：

- 用户简历；
- 项目文档；
- 面经复盘；
- 八股题库；
- JD；
- 个人薄弱点。

### 12.2 RAG 的使用场景

适合场景：

- JD 匹配简历；
- 根据项目文档生成深挖问题；
- 模拟面试读取历史复盘；
- 根据薄弱点推荐题目；
- 周复盘时检索过去记录。

### 12.3 RAG 技术路线

v0.1：

- 不做向量库；
- 用结构化表和全文字段；
- 通过关键词和分类过滤。

v0.2：

- 加入 embedding；
- 使用 Chroma / FAISS / pgvector；
- 对简历、项目文档、面经做检索。

v0.3：

- 加 rerank；
- 加引用来源；
- 加回答可追溯。

## 13. 后端技术方案

### 13.1 推荐技术栈

第一阶段推荐 Python + FastAPI。

原因：

- 写 Agent 编排更快；
- AI SDK 生态更成熟；
- 适合快速接飞书 API 和 DeepSeek；
- 对当前项目验证更友好。

但如果未来要强化后端面试，也可以用 Java/Spring Boot 重写或做第二版。

### 13.2 具体技术选型

- Web 框架：FastAPI；
- ORM：SQLAlchemy 或 SQLModel；
- 数据库：SQLite 起步，后续 PostgreSQL；
- 定时任务：APScheduler 起步，后续 Celery / Redis Queue；
- LLM：DeepSeek OpenAI Compatible API；
- 配置管理：pydantic-settings；

## 15. 关键流程细化

## 15.1 每日计划生成

输入：

- 用户目标岗位；
- 未完成任务；
- 近期薄弱点；
- 面试安排；
- LeetCode 题库；
- 八股题库；
- 最近完成情况。

输出：

- 今日任务列表；

- 分数；
- 通过状态；

- 缺失点；
- 错误点；
- 推荐回答；
- 后续追问。

- 提取公司；
- 提取岗位；
- 提取方向；

## 15.4 面试复盘

输入：

- 结构化提取问题；
- 判断薄弱点；
- 更新投递状态；
- 写入面试复盘表；
- 生成补强任务；
- 推送复盘总结。

## 16. Prompt 设计

### 16.1 总控 Agent Prompt 原则

总控 Agent 应该遵守：

- 不生成空泛建议；
- 能调用工具就调用工具；
- 不直接编造用户数据；
- 需要确认时向用户追问；
- 每次输出都尽量带下一步动作；
- 计划要小而具体；
- 对用户拖延要温和但明确。

### 16.2 八股评分 Prompt 输出格式

建议要求模型输出 JSON，便于系统解析：

```json
{
  "score": 75,
  "result": "weak_pass",
  "covered_points": ["说到了扩容阈值", "说到了容量翻倍"],
  "missing_points": ["没讲清楚 JDK 1.8 扩容迁移优化"],
  "wrong_points": [],
  "feedback": "核心方向正确，但表达还不够完整。",
  "suggested_answer": "面试中可以这样说：...",
  "follow_up_questions": ["为什么 HashMap 容量是 2 的幂？"]
}
```

### 16.3 面试复盘 Prompt 输出格式

```json
{
  "company": "深信服",
  "round": "一面",
  "asked_topics": ["HashMap", "Redis 缓存击穿", "云聚图库权限设计"],
  "weaknesses": [
    {
      "title": "Redis 缓存击穿",
      "category": "八股",
      "severity": "high",
      "reason": "用户明确表示答得不好"
    }
  ],
  "action_items": [
    {
      "title": "复习 Redis 缓存击穿、穿透、雪崩",
      "task_type": "interview_question",
      "priority": "high"
    }
  ],
  "summary": "本次面试主要暴露 Redis 和项目权限设计表达问题。"
}
```

## 19. 风险与取舍

### 19.1 范围过大风险

风险：

- LeetCode、八股、投递、复盘、模拟面试都想做，容易拖慢。

解决：

- 严格按 Phase 做；
- 每个 Phase 都有可运行结果；
- 第一版只做文本和表格；
- 语音和 RAG 后置。

### 19.2 飞书 API 调试风险

风险：

- 飞书应用配置复杂；
- 回调需要公网地址；
- 权限申请和事件订阅容易踩坑。

解决：

- 先用本地 FastAPI + ngrok/Cloudflare Tunnel 调通回调；
- 单独写 feishu-setup 文档；
- 先实现发送普通文本消息，不急着做卡片。

### 19.3 AI 输出不稳定风险

风险：

- 模型可能输出格式不稳定；
- 评分可能前后不一致；
- 任务计划可能过大。

解决：

- 关键输出要求 JSON；
- 后端做 schema 校验；
- 计划生成后做规则过滤；
- AI 只给建议，状态变更由工具执行。

### 19.4 用户懒得用风险

风险：

- 系统做出来，但用户仍然不打卡。

解决：

- 每日任务必须少而具体；
- 晚上追问未完成原因；
- 允许延期，但要记录；
- 周报暴露真实执行情况；
- 不要生成过重计划。

## 20. 面向秋招简历的项目包装

项目名称：

OfferPilot：面向计算机秋招的个人求职 Agent

项目描述：

基于飞书机器人、多维表格和自研 Agent 后端实现的秋招执行系统，围绕计算机学生求职过程中的刷题、八股、投递、面试复盘和模拟面试构建闭环。系统通过大模型进行意图识别、任务规划、回答评分和复盘分析，并通过 Tool Calling 调用任务、投递、题库和飞书工具，实现从用户自然语言输入到结构化数据沉淀和后续任务生成的自动化流程。

可写技术栈：

- Python；
- FastAPI；
- DeepSeek OpenAI Compatible API；
- 飞书开放平台；
- 飞书多维表格；
- SQLite / PostgreSQL；
- Tool Calling；
- RAG；
- APScheduler；
- Docker。

简历亮点：

- 设计并实现 Agent 编排层，将用户自然语言请求路由到任务管理、投递记录、面试复盘、模拟面试等工具；
- 基于飞书开放平台实现机器人消息回调与主动推送，通过多维表格沉淀任务、投递和复盘数据；
- 构建面试复盘分析流程，自动从复盘文本中提取知识点、项目追问和薄弱点，并生成后续补强任务；
- 实现八股与 LeetCode 半自动打卡机制，结合标准答案和核心考点对用户回答进行评分；
- 设计项目深挖模拟面试模块，基于简历、项目文档、岗位 JD 和历史薄弱点进行多轮追问与反馈。

面试时可以这样介绍：

```text
这个项目是我为秋招准备做的个人 Agent。我的痛点是刷题、八股、投递和面试复盘都很分散，而且面试失败后没有形成训练闭环。所以我用飞书作为入口和工作台，自己写了一个 FastAPI 后端做 Agent 编排，接 DeepSeek 进行意图识别、任务规划、回答评分和面试复盘，再通过飞书多维表格沉淀结构化数据。

它和普通聊天机器人不同的点是有状态、有工具调用、有任务闭环。比如我面试后提交一段复盘，系统会自动提取我没答好的知识点，更新薄弱点表，并生成接下来几天的复习和模拟面试任务。
```

## 23. 文档结论

OfferPilot 的需求是成立的，且适合当前阶段。

它既能解决实际秋招准备中的执行问题，也能作为一个可写入简历的 Agent 应用项目。项目不应该从实时语音、复杂 RAG、自动刷题检测开始，而应该先完成“飞书入口 + 后端 Agent 编排 + 多维表格数据沉淀 + 每日任务/复盘闭环”。

第一版的核心不是炫技，而是把闭环跑通：

```text
今天该做什么 -> 用户做了什么 -> AI 怎么评价 -> 明天应该补什么
```

只要这个闭环真实可用，OfferPilot 就不是一个空壳 Agent，而是一个有业务场景、有状态流转、有工具调用、有数据沉淀的完整 AI 应用项目。
